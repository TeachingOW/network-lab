Background

What io_uring is

io_uring is Linux’s interface for asynchronous input and output. The program and the kernel share two queues in memory, so they can exchange many requests without a system call for each one.

Submission queue

The program writes what it wants done: accept a connection, receive, send.

Completion queue

The kernel writes the result of each operation here when it finishes.

One call for many

A single system call hands over every queued request and collects every finished one.

With the older epoll interface every read and every send is its own system call: about twice the kernel time per request here

4 / 30

Some background before the optimisations. A server spends most of its time asking the kernel to do things: accept a connection, read from a socket, write to one. Each of those is normally a system call, and a system call is expensive compared with ordinary code. io_uring, added to Linux in 2019, replaces most of those calls with two ring-shaped queues that live in memory shared between the program and the kernel. The program puts requests on the submission queue, the kernel puts results on the completion queue, and one call, io_uring_enter, moves a whole batch in each direction. bulkapi also has an epoll backend, the older interface, where the kernel only reports which sockets are ready and the program then makes one call per read and one per send. On the same workloads it cost about twice the kernel time per request.

Background · in code

The event loop

for (;;) {
  io_uring_submit_and_wait(&ring, 1);
  io_uring_for_each_cqe(&ring, head, cqe) {
    seen++;
    u64 op = cqe->user_data & OP_MASK;
    Conn* c = (Conn*)(cqe->user_data & ~OP_MASK);
    if (op == OP_RECV)
      on_recv(c, cqe->res, cqe->flags);
    else if (op == OP_SEND)
      on_send(c, cqe->res);
  }
  io_uring_cq_advance(&ring, seen);
}

One call does both jobs. submit_and_wait hands the kernel everything queued since the last turn, then sleeps until at least one operation has finished.

Each completion says whose it is. user_data is a tag the program attached when it submitted: here the connection’s address, with the operation type in its lowest three bits.

cq_advance tells the kernel those results have been read.

Abridged from backend_uring_ms.cpp (accept handling left out)

5 / 30

This is the whole server loop, with the accept branch removed for space. Each turn makes one system call. That call submits whatever was queued during the previous turn, such as sends for the replies just produced, and blocks until the kernel has at least one result. The loop then walks the completion queue. A completion is 16 bytes: a result code, some flags, and user_data, a 64-bit value copied back unchanged from the submission. bulkapi stores the connection pointer there. Because the connection object is aligned to at least 8 bytes, its lowest three bits are always zero, so the operation type, receive or send, is packed into them and masked off here. Finally cq_advance moves the queue’s head so the kernel can reuse those slots.

cqes is the kernel’s completion queue, mapped into Java as a direct ByteBuffer. Java reads results straight out of shared memory.

enter() is the only call that leaves Java: one per turn, however many requests it covers.

The tag is an index, not a pointer: Java has no addresses, so user_data holds the connection’s position in a list.

Abridged from UringBackend.java · liburing sets the ring up through a small JNI shim, native/uring_jni.c

6 / 30

Java cannot call io_uring directly on JDK 11, so the usual approach is a native call for every operation, which is slow because crossing from Java into native code has a fixed cost. This port avoids that. A small C shim uses liburing once to create the ring and returns the memory addresses of the two queues. Java wraps those addresses as direct byte buffers and from then on reads completions and writes submissions itself, exactly as the C++ code does through pointers. getAcquire and setRelease are the Java equivalents of the atomic loads and stores the kernel expects on the queue’s head and tail. The single remaining native call is io_uring_enter, once per loop turn. The tag on each operation is the connection’s index in a list shifted left by three bits, with the operation type in the low bits, because Java objects have no stable address to store.

Background

Single-shot and multishot

Single-shot

One submission gives one completion. To receive the next request, the program must submit a new receive.

The program says which buffer to fill, so each connection needs its own.

--backend uring

Multishot

One submission stays armed and gives a completion every time data arrives. Nothing is resubmitted.

The kernel picks a buffer from a pool shared by all connections on the thread.

--backend uring-ms

Accepting connections was multishot in both backends from the start; the difference is in receiving

7 / 30

These two words describe how long a submission lasts. A single-shot operation is used up by its first result: submit one receive, get one completion, and submit again for the next request. Because the program names the buffer when it submits, each connection needs a buffer of its own waiting to be filled. A multishot operation stays in place after it completes. One receive is submitted when the connection opens, and from then on the kernel posts a completion each time data arrives. Since the program is not there to name a buffer each time, the kernel takes one from a ring of buffers the program registered in advance, shared by every connection on that thread. That sharing is what makes the memory saving on the next slides possible. bulkapi has one backend of each kind.

The first implemented change is a second io_uring backend, selected with backend uring-ms. It uses io_uring_prep_recv_multishot from liburing 2.15: one submission per connection, and the kernel posts a completion for each chunk of data into a buffer taken from a shared ring of 1,024 buffers of 16 kilobytes. The measured effect is a trade-off, not a plain win. Multishot costs about 15 microseconds per request whatever the connection count. Single-shot costs about 9 at 256 connections but 27 at 2,000. So multishot is the backend for thousands of connections and single-shot for a few hundred or fewer. Why single-shot degrades with connection count has not been established.

Optimisation 1 · in code

Arming a multishot receive

void prep_recv_multishot(Conn* c) {
  io_uring_sqe* e = sqe();
  io_uring_prep_recv_multishot(
      e, c->fd, nullptr, 0, 0);
  e->flags |= IOSQE_BUFFER_SELECT;
  e->buf_group = kBufGroup;
  io_uring_sqe_set_data64(e, (u64)c | OP_RECV);
  c->recv_armed = true;
}

// later, on each completion
if (!(flags & IORING_CQE_F_MORE))
  c->recv_armed = false;

No buffer is named. The buffer argument is null and the length is 0. The kernel will choose a buffer each time data arrives.

BUFFER_SELECT and buf_group say which shared pool to take that buffer from.

F_MORE on a completion means the receive is still armed. When it is missing, for example because the pool ran dry, the loop arms it again.

From backend_uring_ms.cpp · io_uring_prep_recv_multishot needs liburing 2.3 or newer and Linux 6.0 or newer

9 / 30

This function runs once when a connection is accepted. sqe() returns the next free slot on the submission queue. io_uring_prep_recv_multishot fills it in as a receive that stays armed. Unlike a normal receive, it is given no buffer and a length of zero, because the program will not be there to supply one for each arrival. The two lines after it tell the kernel to pick a buffer from buffer group zero, the ring of 1,024 buffers this worker registered at startup. The tag is the connection pointer with the receive marker. On the way back, every completion carries a flag called F_MORE while the operation remains armed. If a completion arrives without it, the multishot has ended, which happens when the buffer pool is empty or on an error, and the connection is put on a list to be armed again at the end of the turn.

Optimisation 2 · implemented

No buffer per connection

What changed. A request is parsed in place in the shared receive buffer, with no copy. A private buffer exists only while a request is incomplete, and is freed after.

Result. Memory per idle connection fell 14-fold. Speed is unchanged.

The multishot backend already received into shared buffers, but it copied every request into a 16 kilobyte buffer owned by the connection. Now the request is parsed directly in the shared buffer. Only two cases still need a private buffer: a request that has not fully arrived, and input that arrives while a reply is being sent. That buffer is freed as soon as it is drained. Output buffers are borrowed from a per-worker pool only while a reply exists. Measured with 20,000 connections that each made one request and then sat idle, memory per connection went from 4.54 kilobytes to 0.30. The single-shot backend still holds 4.33 kilobytes. An earlier estimate of 16 kilobytes per connection was wrong: only the touched part of each buffer stays in memory.

Optimisation 2 · how it works

How the memory was reduced

1. The cost before

Every connection owned a 16 KB buffer. Memory comes in 4 KB pages, and the first page is in use as soon as the buffer exists: 4 KB per connection.

2. Share the buffers

Data now lands in a pool of 1,024 buffers per thread. The pool costs about 4 MB once, however many connections there are.

3. Read it in place

The request is handled straight from the shared buffer, which is then handed back. The connection keeps only a record of about 95 bytes.

A private buffer is still created when a request arrives in pieces, and is freed once the request is complete.

Opening 20,000 connections added 80 MB before and 1.9 MB after · the kernel’s own 4 KB per socket is unchanged

11 / 30

This slide explains the mechanism behind the previous number. The operating system gives out memory in pages of 4 kilobytes and only counts a page once something is written to it. Allocating a 16 kilobyte buffer writes a small bookkeeping header at its start, so the first page is in use immediately, and a small request lands in the same page. That is why each connection cost about 4 kilobytes, not 16. The fix has two parts. First, with multishot receive the kernel fills buffers from a shared pool, 1,024 buffers per thread; touching one page of each is about 4 megabytes, a fixed cost. Second, the server no longer copies the request out of that shared buffer: it parses it where it is and returns the buffer straight away. What remains per connection is a small record. The measurement: opening 20,000 connections added 80 megabytes before and 1.9 megabytes after, about 95 bytes each. The reference server reaches the same place a different way, with a 40-byte record in a table allocated at startup. None of this changes the kernel’s own memory, roughly 4 kilobytes per open socket.

Optimisation 2 · in code

Parsing in the shared buffer

void feed(Conn* c, char* p, size_t n) {
  if (c->in_len || c->sending) {
    stash(c, p, n);        // keep a copy
    if (!c->sending) run(c);
    return;
  }
  c->in = p;               // parse in place
  c->in_cap = c->in_len = n;
  process(*c, w);
  size_t left = c->in_len;
  c->in = nullptr;
  c->in_cap = c->in_len = 0;
  if (left) stash(c, p, left);
  after_process(c);
}

p is the kernel’s shared buffer. In the common case the connection simply points at it, the request is handled, and the pointer is cleared. Nothing is copied.

left is what remains of an incomplete request. Only that is copied to a private buffer.

The first branch covers a connection that already holds input or is mid-reply: its bytes must be kept, because p goes back to the kernel on return.

Abridged from backend_uring_ms.cpp (output-buffer pooling and backpressure left out)

12 / 30

feed is called for every chunk of data the kernel delivers, with a pointer into one of the shared buffers and a length. The parser, process, works on whatever the connection’s in pointer refers to, so the trick is to aim that pointer at the shared buffer for the length of one call. process handles every complete request it finds and moves any incomplete remainder to the front. Afterwards the connection lets go of the buffer. If something was left over, a request whose body has not all arrived, stash copies just that part into a heap buffer sized for the whole request, and later chunks are appended to it. The top branch is the other case where a copy is unavoidable: the connection already has saved input, or a reply is still being sent and the output buffer cannot be appended to, so the new bytes are saved for after the send. The caller returns the shared buffer to the kernel as soon as feed returns, which is why nothing may keep pointing into it.

Optimisation 3 · implemented, no measurable gain

Result. The copy is gone, but it was not where the time went.

The reference server writes each response body once into its arena and places the headers in front of it. bulkapi built the body in a scratch string and then copied it into the connection’s output buffer. That copy is now removed for all three backends. A handler writes its body directly after a 160-byte gap. Small bodies, up to 4 kilobytes, are then moved down against the header. Larger bodies stay where they are and the header is padded with spaces in front of the Content-Length value, which HTTP allows. Responses are otherwise byte-identical to before. The measured effect is nothing beyond noise: about 45 microseconds per bulk get of 100 items before and after. This was first on the earlier list of expected gains, and the measurement says it should not have been.

begin_response leaves a 160-byte gap in the output buffer. The handler’s body lands right after it, because res.body is the output buffer.

Large body (over 4 KB): it stays put. The header is padded with spaces so it fills the gap exactly.

Small body: it is moved down against the header. Copying a few bytes is cheaper than sending 90 spaces.

Abridged from http.cpp · the padding goes in front of the Content-Length value, which HTTP permits

14 / 30

The difficulty with writing a response once is that the header contains the body’s length, which is not known until the body is finished. The top four lines show the approach. begin_response reserves 160 bytes and returns where they start. The response object handed to the handler holds a reference to the connection’s output buffer, so every append the handler makes goes directly into place. finish_response then builds the header. For a body larger than 4 kilobytes, it fills the unused part of the gap with spaces placed before the Content-Length number, which the HTTP grammar allows as optional whitespace, so the body never moves. For a small body it writes a normal compact header and slides the body down to meet it, since moving a few hundred bytes costs less than transmitting the padding on every small reply. The handlers themselves did not have to change.

Abridged from Http.java and Out.java · the Java port was written this way from the start

15 / 30

The Java port had this design from its first version, and the C++ change copied it. The three lines at the top are the whole of it from the request handler’s point of view: reserve room, let the handler append, then finish. Inside finish, the header is assembled in a small reusable byte array. For a body over 4 kilobytes the spare room in the gap is filled with spaces before the length digits, so the body is never moved. For a small body the header is written compactly and the body is slid down to meet it. In Java that move is expressed by taking a second view of the same buffer with duplicate, limiting it to the body’s range, and putting it back into the buffer at the earlier position; for a direct buffer this becomes a single overlapping memory move. Using a direct buffer matters in Java: writing a heap array to a socket makes the runtime copy it off-heap first.

The reference waits for 64 completions or 2 milliseconds before each batch. That helps it at high connection counts and costs it a 2 millisecond floor at low ones: with 16 connections it managed 6,500 requests per second against 59,000 for bulkapi. So bulkapi got a load-adaptive version: it only waits when the previous turn was busy, for half as many completions again, up to a time limit set by the BULKAPI_BATCH_US environment variable. With limits of 200 and 1,000 microseconds, CPU per request did not move consistently at 16, 256 or 2,000 connections. The option stays in the code, switched off by default. It may behave differently on a machine where the load generator does not share the cores.

From backend_uring_ms.cpp · batch_us comes from the BULKAPI_BATCH_US environment variable and defaults to 0, which is off

17 / 30

Batching means letting several completions accumulate before waking the server thread, so that each wake-up does more work. The risk is latency: a request that arrives alone waits for company that never comes. This code only takes that risk when the previous turn was already busy. If the last turn handled 32 or more completions, the loop asks the kernel to wait for half that number, capped at 64, with a time limit. Otherwise it behaves exactly as before and wakes on the first completion. The reference applies its batching much earlier, once a turn has seen 8 completions, and with a 2 millisecond limit; that is why it handled 6,500 requests per second with 16 connections against bulkapi’s 59,000. In the measurements this adaptive version neither helped nor hurt, so it is switched off unless the environment variable is set.

The Java port serves the same API from the same spec file, with three ways of doing input and output. The io_uring backend uses a small native shim to set the ring up, and then Java reads and writes the two queues directly in shared memory, so the only native call per loop turn is io_uring_enter. The epoll backend uses Java’s selectors, which are epoll on Linux, one per thread. The sockets backend is the simplest: a blocking socket and one pooled thread per connection. Among the three, io_uring leads everywhere. Epoll is about a fifth behind. Blocking sockets do well on bulk requests, where the work per request is large, but fall to between a quarter and a half of io_uring on small unpipelined requests, with a worst-case latency three to eight times higher, because 256 connections means 256 threads competing for four cores. Compared with the C++ server, Java io_uring is within noise on throughput. It already has two of the open C++ optimisations, an open-addressing store and a response written once. The clear cost is memory: about 350 megabytes against 20, most of it the Java heap that was sized at 1 gigabyte for the test.

Java epoll backend

for (;;) sel.select(this::onKey);

private void onKey(SelectionKey key) {
  Conn c = (Conn) key.attachment();
  if (c == null) { accept(); return; }
  c.ensureRoom();

  in.limit(in.capacity()).position(c.inLen);

A Selector is epoll. On Linux, Java’s selector is built on it. It reports which sockets are ready; the program then reads and writes them itself.

select(this::onKey) calls the method for each ready socket without building a set of keys first.

OP_WRITE is requested only when a reply does not fit in the socket in one go.

Abridged from EpollBackend.java (the write-ready branch and error handling left out) · one selector per thread

20 / 30

This is the readiness model, the one io_uring replaces. The selector tells the thread that a socket has data, and the thread then makes its own read call and its own write call: two system calls per request plus the wait, against io_uring’s shared queues. Each worker thread has its own selector and its own listening socket on the same port, so the kernel spreads new connections across threads and no connection is ever touched by two threads. Two details keep it lean. The form of select that takes a callback avoids allocating and clearing a set of ready keys on every turn. And the connection is only registered for write readiness when a reply could not be written in full, which is rare; in the normal case the reply is written straight after the request is handled. The read goes into a direct buffer at the position after any bytes already held.

  ByteBuffer b = c.out.b;
  if (b.position() == 0) continue;
  b.flip();
  while (b.hasRemaining()) ch.write(b);
  c.out.clear();
}

One thread per connection. The thread sleeps inside read() until the client sends something. There is no event loop at all.

The same parser. Http.process is shared by all three Java backends; only the way bytes arrive and leave differs.

The cost: 256 connections means 256 threads competing for 4 cores, which is why it falls behind on small requests.

Abridged from SocketsBackend.java · threads come from a cached pool, so they are reused across connections

21 / 30

This is the simplest possible server and the one most Java code was written as for years. Each accepted connection is handed to a thread from a pool, and that thread runs this loop until the connection closes: block in read, handle whatever complete requests arrived, write the replies, repeat. It needs no selector, no queue and no state machine, because the thread’s own stack holds the state. It does well on bulk requests, where the work per request is large compared with the cost of waking a thread. It does badly on many small requests: with 256 connections there are 256 threads, the operating system has to switch between them on four cores, and worst-case latency was three to eight times that of the io_uring backend. On a newer JDK, virtual threads would remove much of that cost while keeping this code almost unchanged; only JDK 11 is installed here.

The store the C++ server should copy

private long[] keys = new long[16];
private byte[][] vals = new byte[16][];

byte[] get(long k) {
  int m = keys.length - 1;
  for (int i = slot(k, m); vals[i] != null;
       i = (i + 1) & m)
    if (keys[i] == k) return vals[i];
  return null;
}

private int slot(long k, int mask) {
  return (int) ((k * MIX) >>> 20) & mask;
}

Two flat arrays. Keys are plain 64-bit numbers side by side, with no object and no pointer per entry. A null value marks an empty slot.

A lookup walks forward from the key’s home slot until it finds the key or an empty slot. Neighbouring slots share a cache line.

This is optimisation 5, already built here. The C++ server still uses a node-based map.

From Store.java · 256 such shards, each locked separately · Java bulk get measured 62–63k req/s against C++ 43–54k

22 / 30

This is one shard of the Java store. Java’s built-in HashMap would box every 64-bit key into an object and wrap every entry in a node, which is the same shape of cost as the C++ unordered map. Instead the shard keeps keys in a long array and values in an array of byte arrays. To find a key, it multiplies by a large odd constant to scramble the bits, takes some of the high bits as a starting slot, and steps forward one slot at a time. Because the keys sit next to each other in memory, a short walk usually stays within one cache line. Insertion uses the same walk and doubles the arrays when they are three-quarters full; deletion shifts later entries back so walks never hit a false gap. This is exactly what the next slide proposes for the C++ server. In the two-round benchmark the Java io_uring backend did 62 to 63 thousand bulk gets per second against 43 to 54 thousand for C++, which is suggestive but not proof, since the two differ in other ways too.

Optimisation 5 · not done

Replace the store’s hash map

Today

Each shard is a std::unordered_map. Every new item allocates a node, and every lookup follows a pointer to it.

Proposed

An open-addressing table: keys and values in flat arrays, no node per entry, short values stored inline.

Why expect a gain

The reference and the Java port both use this layout. The reference’s bulk get costs about 30 µs against our 43.

Expected, not measured · store.h

23 / 30

This is now the first open item. The store is 256 shards, each a standard unordered map from a 64-bit id to a string. That container allocates one heap node per item and reaches each item through a pointer, so a bulk request of 100 items pays 100 allocations on insert and 100 cache misses on lookup. An open-addressing table keeps keys and values in flat arrays. Both the stripped reference and the Java port already use that layout. The expected gain is on the bulk endpoints, where our own code is 50 to 70 percent of the cost. No number is claimed: this has not been built or measured for the C++ server.

Optimisation 6 · not done

Lock once per shard, not per item

Today

A bulk request of 100 items takes and releases a spinlock 100 times, once for each item.

Proposed

Group the batch by shard first, then take each shard’s lock once and handle all of its items together.

Trade-off

Bulk get must still return items in request order, so grouping needs a second pass. It pays most with several threads.

Expected, not measured · handlers.cpp

24 / 30

The bulk handlers lock and unlock a shard for every single item. With one thread the locks are never contended, so each costs only two atomic operations, but with four threads working on the same shards they start to bounce cache lines between cores. Grouping a batch by shard means at most one lock per shard touched. The cost is that bulk get has to produce output in the order the ids were given, so the lookups would be done grouped and the results written in a second pass. The reference avoids the question entirely by having one thread own the store. This is expected to matter more as thread count goes up, and has not been measured.

Optimisation 7 · not done

Faster JSON output

Today

Escaping checks one byte at a time, and each item is built from several small appends that may each regrow the buffer.

Proposed

Scan 16 bytes at a time for a character that needs escaping, copy clean runs in one go, and reserve the response size up front.

Why expect a gain

Bulk get is 70% our own code, and its output is almost all escaped values. The reference already scans 16 bytes at a time.

Expected, not measured · json.cpp, handlers.cpp

25 / 30

Every value returned by a get or a bulk get passes through json_escape, which tests each byte for a quote, a backslash or a control character. Almost every byte passes, so the work is a long run of checks that find nothing. The reference tests 16 bytes at once using compiler vector extensions and copies the whole clean run with one memcpy. The second half of this item is reserving the output size before a bulk get starts, since the number of ids is known, so the output buffer does not regrow many times. With the response copy now gone and no gain seen from it, this and the store are the two remaining differences between our bulk get path and the reference’s.

Optimisation 8 · not done

One system call per request

Today. With a single client, the single-shot backend enters the kernel twice per request: once for the receive completion, once for the send completion.

Proposed. Link the send to the next receive and suppress the send’s completion, so one entry covers both.

26 / 30

This one only matters at low concurrency. Counting system calls showed exactly two io_uring_enter calls per request with a single client, and about 0.03 with 64, because a busy loop already handles many completions per entry. The fix is to submit the send and the following receive as a linked pair, mark the send so it posts no completion on success, and use MSG_WAITALL so a short send becomes an error instead of breaking the link. That halves both the kernel entries and the completions per request in the low-load case. The multishot backend partly has this already, since its receive is never resubmitted. The 64-client figure was taken under strace, which slows the server and makes batching look better than it is.

The kernel is 73–91% of the cost of a small request, so this is the only route to a faster single GET. Each item is small, and none has been measured here.

Expected, not measured · the reference uses the first three and the last

27 / 30

These are grouped because each is a small saving inside the kernel. Direct descriptors mean accepted sockets live in a table registered with the ring, so each operation skips looking the file up and taking a reference on it. Registering the ring’s own descriptor does the same for io_uring_enter. Setting TCP no-delay once on the listening socket, which accepted sockets inherit, removes a setsockopt call per connection. Zero-copy send avoids copying a response into the kernel, but it only pays above roughly ten kilobytes and gives nothing over loopback, which is how everything here was measured. The idle timeout is not about speed: bulkapi never closes a stalled connection, and the reference closes them after 90 seconds. Direct descriptors need a linked cancel, shutdown and close sequence, which makes the close path more complex.

Before more speed · not done

Three defects to fix first

Unicode escapes corrupt data

Inserting “café” stores “cafu00e9”. The backslash is dropped. The Java port and the reference decode it correctly.

Allocations are unchecked

A failed allocation for a 64 MB body is a crash. The reference checks every one.

Header values are not trimmed

A Content-Length with a trailing space is answered 400. The Java port and the reference accept it.

All three confirmed against the running C++ server · json.cpp, conn.cpp, http.cpp

28 / 30

None of these is an optimisation, but the first one matters more than any of them. The bulk insert reader treats a backslash-u escape as an unknown escape and keeps only the letter u, so any non-ASCII text sent in escaped form is silently stored wrong. It was confirmed by inserting a value and reading it back. The second is that malloc and realloc results are never checked, in three places. The third is a small protocol strictness: a header value with trailing whitespace is rejected. The Java port fixes the first and third, which is why it differs from the C++ server on exactly two probe lines. There are also no automated tests; every check in this deck was a probe run by hand.
