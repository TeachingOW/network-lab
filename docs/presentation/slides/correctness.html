Three defects to fix first

Unicode escapes corrupt data

Inserting “café” stores “cafu00e9”. The backslash is dropped. The Java port and the reference decode it correctly.

Allocations are unchecked

A failed allocation for a 64 MB body is a crash. The reference checks every one.

Header values are not trimmed

A Content-Length with a trailing space is answered 400. The Java port and the reference accept it.

All three confirmed against the running C++ server · json.cpp, conn.cpp, http.cpp

28 / 30

None of these is an optimisation, but the first one matters more than any of them. The bulk insert reader treats a backslash-u escape as an unknown escape and keeps only the letter u, so any non-ASCII text sent in escaped form is silently stored wrong. It was confirmed by inserting a value and reading it back. The second is that malloc and realloc results are never checked, in three places. The third is a small protocol strictness: a header value with trailing whitespace is rejected. The Java port fixes the first and third, which is why it differs from the C++ server on exactly two probe lines. There are also no automated tests; every check in this deck was a probe run by hand.
