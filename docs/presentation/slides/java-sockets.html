while (!c.wantClose) {
  c.ensureRoom();
  ByteBuffer in = c.in;
  in.limit(in.capacity()).position(c.inLen);
  int n = ch.read(in);    // blocks this thread
  if (n < 0) break;
  c.inLen += n;
  Http.process(c, w);
  ByteBuffer b = c.out.b;
  if (b.position() == 0) continue;
  b.flip();
  while (b.hasRemaining()) ch.write(b);
  c.out.clear();
}

One thread per connection. The thread sleeps inside read() until the client sends something. There is no event loop at all.

The same parser. Http.process is shared by all three Java backends; only the way bytes arrive and leave differs.

The cost: 256 connections means 256 threads competing for 4 cores, which is why it falls behind on small requests.

This is the simplest possible server and the one most Java code was written as for years. Each accepted connection is handed to a thread from a pool, and that thread runs this loop until the connection closes: block in read, handle whatever complete requests arrived, write the replies, repeat. It needs no selector, no queue and no state machine, because the thread’s own stack holds the state. It does well on bulk requests, where the work per request is large compared with the cost of waking a thread. It does badly on many small requests: with 256 connections there are 256 threads, the operating system has to switch between them on four cores, and worst-case latency was three to eight times that of the io_uring backend. On a newer JDK, virtual threads would remove much of that cost while keeping this code almost unchanged; only JDK 11 is installed here.
