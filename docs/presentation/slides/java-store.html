The store the C++ server should copy

private long[] keys = new long[16];
private byte[][] vals = new byte[16][];

byte[] get(long k) {
  int m = keys.length - 1;
  for (int i = slot(k, m); vals[i] != null;
       i = (i + 1) & m)
    if (keys[i] == k) return vals[i];
  return null;
}

private int slot(long k, int mask) {
  return (int) ((k * MIX) >>> 20) & mask;
}

Two flat arrays. Keys are plain 64-bit numbers side by side, with no object and no pointer per entry. A null value marks an empty slot.

A lookup walks forward from the key’s home slot until it finds the key or an empty slot. Neighbouring slots share a cache line.

This is optimisation 5, already built here. The C++ server still uses a node-based map.

This is one shard of the Java store. Java’s built-in HashMap would box every 64-bit key into an object and wrap every entry in a node, which is the same shape of cost as the C++ unordered map. Instead the shard keeps keys in a long array and values in an array of byte arrays. To find a key, it multiplies by a large odd constant to scramble the bits, takes some of the high bits as a starting slot, and steps forward one slot at a time. Because the keys sit next to each other in memory, a short walk usually stays within one cache line. Insertion uses the same walk and doubles the arrays when they are three-quarters full; deletion shifts later entries back so walks never hit a false gap. This is exactly what the next slide proposes for the C++ server. In the two-round benchmark the Java io_uring backend did 62 to 63 thousand bulk gets per second against 43 to 54 thousand for C++, which is suggestive but not proof, since the two differ in other ways too.
