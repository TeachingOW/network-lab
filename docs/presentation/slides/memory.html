Optimisation 2 · how it works

How the memory was reduced

1. The cost before

Every connection owned a 16 KB buffer. Memory comes in 4 KB pages, and the first page is in use as soon as the buffer exists: 4 KB per connection.

2. Share the buffers

Data now lands in a pool of 1,024 buffers per thread. The pool costs about 4 MB once, however many connections there are.

3. Read it in place

The request is handled straight from the shared buffer, which is then handed back. The connection keeps only a record of about 95 bytes.

A private buffer is still created when a request arrives in pieces, and is freed once the request is complete.

Opening 20,000 connections added 80 MB before and 1.9 MB after · the kernel’s own 4 KB per socket is unchanged

This slide explains the mechanism behind the previous number. The operating system gives out memory in pages of 4 kilobytes and only counts a page once something is written to it. Allocating a 16 kilobyte buffer writes a small bookkeeping header at its start, so the first page is in use immediately, and a small request lands in the same page. That is why each connection cost about 4 kilobytes, not 16. The fix has two parts. First, with multishot receive the kernel fills buffers from a shared pool, 1,024 buffers per thread; touching one page of each is about 4 megabytes, a fixed cost. Second, the server no longer copies the request out of that shared buffer: it parses it where it is and returns the buffer straight away. What remains per connection is a small record. The measurement: opening 20,000 connections added 80 megabytes before and 1.9 megabytes after, about 95 bytes each. The reference server reaches the same place a different way, with a 40-byte record in a table allocated at startup. None of this changes the kernel’s own memory, roughly 4 kilobytes per open socket.
