Single-shot and multishot

Single-shot

One submission gives one completion. To receive the next request, the program must submit a new receive.

The program says which buffer to fill, so each connection needs its own.

--backend uring

Multishot

One submission stays armed and gives a completion every time data arrives. Nothing is resubmitted.

The kernel picks a buffer from a pool shared by all connections on the thread.

--backend uring-ms

Accepting connections was multishot in both backends from the start; the difference is in receiving

7 / 30

These two words describe how long a submission lasts. A single-shot operation is used up by its first result: submit one receive, get one completion, and submit again for the next request. Because the program names the buffer when it submits, each connection needs a buffer of its own waiting to be filled. A multishot operation stays in place after it completes. One receive is submitted when the connection opens, and from then on the kernel posts a completion each time data arrives. Since the program is not there to name a buffer each time, the kernel takes one from a ring of buffers the program registered in advance, shared by every connection on that thread. That sharing is what makes the memory saving on the next slides possible. bulkapi has one backend of each kind.
